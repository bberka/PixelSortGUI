# Drift engine architecture research

**Research date requested:** 2026-11-24. **Verification status:** The initial draft was written without live web search; browser support versions, storage quotas, eviction rules, canvas limits, and encoder capabilities below were verified against live primary sources on 2026-11-24 (see **Verification pass** at the end). Performance targets in §3 remain proposed engineering targets, not measured benchmarks.

## 1. Compute path for pixel sorting

**Recommendation: begin with TypeScript typed-array kernels in a Web Worker, behind a backend interface. Add WebGPU as an optional accelerator after a representative benchmark.** Do not make WebGPU a prerequisite and do not start with shader-only sorting.

| Path | Strengths | Costs / fit |
|---|---|---|
| TypeScript typed arrays + Worker | Universal fallback; straightforward variable-length spans, arbitrary paths, cancellation and deterministic tests; transferable buffers avoid copies. | CPU-bound; optimize memory traffic and avoid repeated full-frame copies. A Worker protects UI responsiveness, not total compute time. |
| Rust/Wasm SIMD + threads | Strong kernel performance potential, portable binary, Rust safety; useful once profiling identifies CPU bottleneck. Wasm 128-bit SIMD is widely supported (Chrome/Edge 91+, Firefox 89+, Safari/iOS 16.4+); Wasm threads/atomics are supported in Chrome/Edge 79+, Firefox 79+, Safari 14.1+ (stabilized by 15.2). | Adds build/toolchain complexity and JS/Wasm data-boundary costs. Wasm threads require `SharedArrayBuffer` and cross-origin isolation (`Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`). GitHub Pages cannot natively set custom HTTP response headers; a service-worker shim (`coi-serviceworker`) can inject them after an initial reload, but adds reload/CORP friction. Single-thread Wasm SIMD in a Worker works without isolation headers. |
| WebGPU compute | Parallel key calculation, masks/span detection, fixed-size sorting and image transforms; can keep intermediate data on GPU. | Variable-length run construction, arbitrary path traversal and scatter/gather are awkward; readback and dispatch overhead may dominate. Must retain CPU fallback and account for adapter/device loss. |
| WebGL2 fragment tricks | Broadly deployed GPU preview and shader compositing. | Fragment pipeline is not general-purpose compute; sorting and data-dependent span traversal require encoding tricks, ping-pong passes and texture constraints. Not the primary sorting engine. |

**Split the work:** CPU owns path ordering, variable-span boundaries, run construction and variable-length ordering. GPU is a good fit for per-pixel sort-key computation, threshold/span masks, preview compositing, and fixed-length block/bitonic sorting where padded blocks are acceptable. A later hybrid can GPU-compute keys/masks, compact or transfer run descriptors, and CPU-sort irregular runs. Avoid moving full-resolution pixels between CPU and GPU more than necessary.

**Verified support snapshot (2026-11-24):** WebGPU now ships enabled by default across all major browser families (~88–90% global coverage on Can I use), though MDN still classifies it as "Limited availability" due to OS/driver gaps, and it requires a secure context (HTTPS):
- **Chrome / Edge desktop:** Enabled by default since **v113** (Windows D3D12, macOS Metal, ChromeOS Vulkan). Linux support is expanding from **Chrome 144+** (initially Intel Gen12+ GPUs).
- **Android Chrome:** Enabled by default since **Chrome 121** on **Android 12+** devices with Qualcomm or ARM GPUs.
- **Safari (macOS, iOS, iPadOS, visionOS):** Enabled by default starting in **Safari 26.0** (Metal backend; requires macOS 26 / iOS 26+).
- **Firefox:** Enabled by default on Windows in **Firefox 141** and on Apple Silicon macOS in **Firefox 145**. Intel Macs, Linux, and Android Firefox remain unshipped / experimental.

Because WebGPU is now available on modern iOS (Safari 26+) and Android (Chrome 121+), it is a stronger phase-2 mobile accelerator than previously assumed. However, the recommendation to start with a TypeScript Worker baseline **still holds**: irregular variable-length pixel-sort spans fit CPU better, and Linux, Intel Mac Firefox, Firefox Android, older iOS (<26), and older Android (<12 or unsupported GPUs) still require the CPU path. Feature-detect `navigator.gpu`, request an adapter/device, and run a tiny compute-pipeline smoke test at startup; treat failure as ordinary fallback.

Sources: [MDN WebGPU API](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API), [Can I use WebGPU](https://caniuse.com/webgpu), [WebGPU specification](https://gpuweb.github.io/gpuweb/), [Chrome WebGPU](https://developer.chrome.com/docs/web-platform/webgpu/), [WebKit Features in Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/), [Firefox 141 Release Notes](https://www.firefox.com/en-US/firefox/141.0/releasenotes/), [Firefox 145 Release Notes](https://www.firefox.com/en-US/firefox/145.0/releasenotes/), [Can I use Wasm SIMD](https://caniuse.com/wasm-simd), [Can I use Wasm Threads](https://caniuse.com/wasm-threads).

## 2. Web versus native

**Answer: start web-first.** The product's offline, local-only, cross-device goals align with a static web app, and the CPU fallback permits a working product without GPU availability. A web core can later be packaged with Tauri (desktop) or Capacitor (mobile), subject to platform APIs and WebView differences. Keep the image engine independent of UI and persistence adapters so the core survives packaging.

Native-first becomes preferable if a tested browser target cannot meet export-time/memory requirements, if reliable access to native GPU APIs or system image codecs is essential, if 24–48 MP mobile exports routinely hit iOS Safari's verified 16.78 MP single-canvas area cap and 384 MB cumulative canvas memory limit (and a tiled/Wasm encode fallback proves too slow or memory-heavy), or if deep OS file workflows/background processing are core requirements. Verify those with a prototype before choosing native: native brings separate packaging, update, platform UI, and maintenance costs and does not automatically solve algorithmic performance.

References: [Tauri architecture](https://tauri.app/concept/architecture/), [Capacitor](https://capacitorjs.com/docs), [WebAssembly portability](https://webassembly.org/).

## 3. Performance targets and preview

These are **proposed product acceptance targets, not measured guarantees**. A 12 MP RGBA8 working buffer alone is about 48 MB; extra source, output, proxy, undo and GPU copies multiply memory use. Phone targets should be verified on actual representative devices.

| Device class | Slider preview | Full-resolution export target (12 MP / 24 MP / 48 MP) |
|---|---:|---:|
| Mid-range laptop | visible update ≤100 ms (p95); interactive proxy ≤50 ms | ≤2 / 5 / 12 seconds |
| Mid-range phone | visible update ≤150 ms (p95); interactive proxy ≤80 ms | ≤5 / 12 / 30 seconds |

Targets assume representative JPEG photos and an agreed quality/algorithm; format, browser, thermal throttling, memory pressure and sort settings can change results substantially. **iOS canvas constraint:** because iOS Safari caps a single `<canvas>` at 16,777,216 pixels (~16.78 MP; see §5), the 24 MP and 48 MP phone export targets cannot rely on a single full-resolution canvas draw/`toBlob()` call on iOS — they require tiled decode plus direct Wasm/JS encoding from typed-array buffers (or capping iOS export at ≤16.78 MP). Report measured p50/p95 and peak memory, not only best run. If targets fail, show progress and permit cancellation rather than freezing or silently degrading output.

**Preview strategy:** decode once; create a resolution-capped proxy (e.g. 1–2 MP on phones, 2–4 MP desktop); recompute proxy while dragging; debounce expensive work only slightly and cancel stale generations; on release, run full-resolution output in tiles or progressive stages. Use generation IDs and cooperative cancellation between rows/tiles. Keep preview and export kernels behaviorally aligned. Avoid queuing every slider event. Transfer buffers or use shared memory only when cross-origin isolation is available.

## 4. Persistence

**Recommendation:** IndexedDB as the portable durable project catalog and blob store; store original compressed image blobs, generated thumbnails, parameters, and compact history records there. Keep undo as parameter snapshots/commands where possible, not a full RGBA frame per step. Consider OPFS for large scratch/intermediate files only after measuring browser support and recovery behavior. File System Access is an import/export convenience, not the sole source of truth.

- **IndexedDB & origin quotas:** Broadly available asynchronous structured storage with Blob support, transactions, and schema migrations. Quotas are dynamic percentages of disk space:
  - **Chrome / Edge (Chromium):** Up to **60% of total disk space** per origin; LRU eviction of best-effort origins begins when total browser storage exceeds **80% of total disk space** (or under disk pressure).
  - **Firefox:** Best-effort temporary pool scales with disk (~10% of total disk per group/eTLD+1), expanding up to ~50% when persistent storage is granted; LRU eviction triggers when local disk space runs critically low.
  - **Safari / iOS (WebKit, Safari 17+):** Up to **60% of total disk space** per origin for browser apps (Safari) and Home Screen web apps, up to **15%** for non-browser apps embedding web content, and up to **80%** overall across all origins.
- **Safari / iOS 7-day eviction rule & Home Screen exemption:** Under WebKit's Intelligent Tracking Prevention (ITP), Safari deletes all script-writable storage (IndexedDB, Cache API, OPFS, Service Workers, `localStorage`) for an origin after **7 days of browser use without user interaction** (click, tap, or key press) with that site. Installing the app via **Add to Home Screen** (iOS) or Dock (macOS) exempts the standalone web app from Safari's browser-tab 7-day cap (its activity counter is tied to use of the Home Screen app itself) and satisfies WebKit's persistence heuristics.
- **`navigator.storage.persist()`:** Supported in Chrome, Edge, Firefox, and **Safari 17.0+** (desktop & iOS). Persistent buckets are exempt from storage-pressure eviction. **Firefox** displays a user permission prompt; **Chrome/Edge** and **Safari** grant or deny automatically via browser heuristics (such as site engagement, bookmarks, or Home Screen/PWA installation) without prompting. Always check `persisted()` rather than assuming a grant.
- **OPFS:** `navigator.storage.getDirectory()` and Worker-only `FileSystemSyncAccessHandle` are widely supported (**Chrome/Edge 86+, Firefox 111+, Safari/iOS 15.2+**); `FileSystemFileHandle.createWritable()` is supported in Chrome 86+, Firefox 111+, and Safari 16.2+ (for OPFS). Still shares the origin quota and eviction policy; useful for large scratch/intermediate files once tested.
- **File System Access API:** User-facing pickers (`showOpenFilePicker`, `showSaveFilePicker`) remain Chromium-only (not supported in Firefox or Safari). Permission can be revoked, and handles are not a dependable replacement for app-managed copies. Always offer import/copy into IndexedDB.
- **Private browsing:** Ephemeral across Chrome Incognito, Firefox Private Browsing, and Safari Private Browsing. Storage APIs generally operate in-memory or in temporary sandboxes so the app functions during the session, `navigator.storage.persist()` is denied or non-durable, and **all stored data is wiped when the private session closes**. *(Exact per-browser private-mode byte caps remain unverified, as they are implementation-defined and vary by device RAM/version.)* Explain that private mode cannot promise session restoration. Never imply browser storage is a backup.

Estimate quota at runtime with `navigator.storage.estimate()`, display storage usage, handle quota errors, maintain an explicit cleanup policy for disposable cache, and write project updates atomically. Request persistent storage and encourage iOS users to add the app to their Home Screen to avoid Safari's 7-day tab eviction. Test restart restoration and quota exhaustion.

Sources: [MDN Storage quotas and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [MDN StorageManager.persist()](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist), [WebKit: Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/), [WebKit: Full Third-Party Cookie Blocking and More (7-day cap)](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/), [MDN IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API), [MDN OPFS](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system), [MDN FileSystemFileHandle.createWritable()](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemFileHandle/createWritable), [MDN File System Access](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API), [web.dev storage](https://web.dev/articles/storage-for-the-web).

## 5. Decode and encode

**Recommendation (updated after verification):** use `createImageBitmap` as the baseline async decode path, normalize orientation and color behavior in a tested decode adapter, process pixels in a Worker, and use `canvas.toBlob`/`OffscreenCanvas.convertToBlob` for **PNG and JPEG** export (and native WebP on Chromium/Firefox). Because **iOS Safari caps a single canvas at 16.78 MP**, **Safari lacks native WebP canvas encoding**, and **no major browser natively supports AVIF canvas encoding**, plan for a lazy-loaded Wasm encoder (e.g. `@jsquash/jpeg`, `@jsquash/png`, `@jsquash/webp`, `@jsquash/avif`) if you need 24–48 MP full-res export on iOS, WebP export on Safari, or AVIF export on any browser. Probe WebCodecs `ImageDecoder` where available, but keep `createImageBitmap` as the universal fallback.

- **`createImageBitmap`:** Baseline Widely Available (**Chrome 50+, Edge 79+, Firefox 42+, Safari/iOS 15+**). Supports `imageOrientation` (`"from-image"`, `"flipY"`, `"none"`: Chrome, Firefox 93+, Safari 15+) and `colorSpaceConversion` (`"default"`, `"none"`: Chrome 50+, Firefox 98+, Safari 15+). Platform color-space mapping quirks still warrant end-to-end testing with EXIF-rotated JPEGs and embedded ICC profiles.
- **`ImageDecoder` (WebCodecs):** Supported in **Chrome/Edge 94+** and **Firefox 133+** (secure contexts and Dedicated Workers). Not supported in Safari 18 (which shipped video/audio WebCodecs only); landed in WebKit trunk / Safari Technology Preview (STP 251), with exact stable Safari release version **unverified**. Do not assume availability on iOS.
- **Verified canvas maximum dimensions, area, and iOS memory limit:**
  - **Chrome / Edge:** max width/height **32,767 px**; max area **268,435,456 px** (`16,384 × 16,384`, ~268.4 MP).
  - **Firefox:** max width/height **32,767 px**; max area **472,907,776 px** (~472.9 MP; older pre-v122 builds were ~124.9M px).
  - **Safari (macOS desktop):** max width/height **32,767 px**; max area **268,435,456 px** (`16,384 × 16,384`).
  - **iOS Safari:** max single-canvas area **16,777,216 px** (`4,096 × 4,096`, ~16.78 MP) — exceeding it invalidates the canvas. Additionally, iOS WebKit enforces a **cumulative canvas memory limit of 384 MB** across active/cached canvases on modern iOS (iOS 15+; **224 MB** on older iOS / low-RAM devices). A 48 MP RGBA buffer is ~192 MB before copies, so iOS cannot hold a single 24 MP or 48 MP canvas. Explicitly shrink unneeded canvases (`canvas.width = 1; canvas.height = 1`) to release WebKit's backing-store cache, and tile/use Wasm encoding for >16.78 MP on iOS.
- **EXIF orientation & color:** normalize once; avoid double-rotation between decoder and export. Define color policy (preserve/convert to sRGB) and test tagged images per chosen decode/export path.
- **Native canvas encoder support (`HTMLCanvasElement.toBlob` / `OffscreenCanvas.convertToBlob`):** Per the HTML specification, unsupported MIME types **silently fall back to `image/png`** rather than throwing. Always verify `blob.type === requestedMime`.
  - **PNG (`image/png`):** Supported everywhere (mandatory per spec; lossless; `quality` ignored).
  - **JPEG (`image/jpeg`):** Supported everywhere (lossy; `quality` 0.0–1.0).
  - **WebP (`image/webp`):** Supported in **Chrome/Edge** (desktop & Android) and **Firefox 96+**. **Not supported in Safari (macOS & iOS)** — silently falls back to `image/png`. Use a Wasm `libwebp` encoder on Safari or fall back to JPEG/PNG.
  - **AVIF (`image/avif`):** **Not natively supported** in `toBlob()` / `convertToBlob()` on Chrome, Edge, Firefox, or Safari (all silently fall back to `image/png`, even though all four decode AVIF). Client-side AVIF export requires a Wasm encoder (e.g. `libavif`).

“Fastest encoder” is hardware/browser-dependent and cannot be declared without measurement. Ship PNG and JPEG first via native canvas encoders; enable native WebP where `blob.type === 'image/webp'` passes a runtime probe; treat Safari WebP, universal AVIF, and >16.78 MP iOS export as optional Wasm-encoder features.

Sources: [MDN createImageBitmap](https://developer.mozilla.org/en-US/docs/Web/API/Window/createImageBitmap), [Can I use createImageBitmap](https://caniuse.com/mdn-api_createimagebitmap), [MDN ImageDecoder](https://developer.mozilla.org/en-US/docs/Web/API/ImageDecoder), [Can I use ImageDecoder](https://caniuse.com/mdn-api_imagedecoder), [WebCodecs spec](https://www.w3.org/TR/webcodecs/), [MDN canvas limits note](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/canvas#maximum_canvas_size), [PQINA canvas size & iOS memory limits](https://pqina.nl/blog/total-canvas-memory-use-exceeds-the-maximum-limit/), [MDN canvas toBlob](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/toBlob), [MDN OffscreenCanvas convertToBlob](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas/convertToBlob), [HTML canvas specification](https://html.spec.whatwg.org/multipage/canvas.html).

## 6. UI stack and responsiveness

**Recommendation: React + TypeScript + Vite, with shadcn/ui and Tailwind, and a small external state store (Zustand or equivalent).** React is the sensible choice because shadcn's canonical component ecosystem is React; leaving React may reduce framework runtime overhead but loses direct compatibility, ecosystem breadth and predictable component reuse. In a canvas-heavy editor, pixel processing dominates, so framework micro-benchmarks are unlikely to outweigh integration cost.

Keep transient slider value local; send throttled parameter snapshots to a Worker; update React only for controls, progress and coarse preview status. Render the canvas imperatively rather than pushing pixel frames through component state. Use `OffscreenCanvas` in a Worker where available, with main-thread canvas fallback. **Verified support:** `OffscreenCanvas` (including 2D context and `convertToBlob`) is Baseline Widely Available across **Chrome 69+, Edge 79+, Firefox 105+, and Safari / iOS Safari 16.4+**. Feature-detect worker transfer anyway for graceful degradation on legacy browsers.

Sources: [shadcn/ui](https://ui.shadcn.com/docs), [React](https://react.dev/), [MDN OffscreenCanvas](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas), [Can I use OffscreenCanvas](https://caniuse.com/offscreencanvas), [MDN Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API).

## 7. Offline and hosting

**Recommendation:** ship a static PWA with a service worker that precaches app shell and versioned assets; no runtime network dependency for editing. Store user images only in origin storage. **Verified PWA installability:**
- **Android Chrome (and Edge/Samsung Internet):** Full PWA installability (requires HTTPS, Web App Manifest with `name`/`start_url`/`display`/`icons`, and a Service Worker with a `fetch` handler). Supports browser-triggered install banners and custom in-app install buttons via the `beforeinstallprompt` event.
- **iOS Safari:** Does **not** support `beforeinstallprompt` (nor does Firefox). Users must install manually via the iOS Share sheet → **"Add to Home Screen"**. Detect installed state with `window.navigator.standalone` or `@media (display-mode: standalone)` and show lightweight instructional UI when running in a Safari tab. Installing on iOS is especially valuable for this app because Home Screen web apps are exempt from Safari's 7-day browser-tab storage eviction rule (§4).

Static hosting is compatible with this architecture. GitHub Pages can host static assets and service workers over HTTPS, but **cannot natively configure custom HTTP response headers** (`COOP`/`COEP`), so cross-origin-isolated Wasm threads do not work out of the box. While a client-side service worker (`coi-serviceworker`) can inject COOP/COEP headers on reload, it introduces an initial reload and strict CORP requirements; avoiding threads in favor of a single-thread Worker (or Wasm SIMD) avoids this complexity. Keep all worker/Wasm/shader assets same-origin and versioned. A service worker does not make external dependencies offline unless cached, so bundle dependencies locally.

Sources: [MDN PWA installability](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable), [MDN beforeinstallprompt](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeinstallprompt_event), [Can I use beforeinstallprompt](https://caniuse.com/mdn-api_window_beforeinstallpromptevent), [Apple Add to Home Screen](https://support.apple.com/guide/iphone/bookmark-a-website-iph42ab2f3a7/ios), [MDN service workers](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API), [MDN cross-origin isolation](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer#security_requirements), [GitHub Pages documentation](https://docs.github.com/en/pages).

## 8. Leave room for later

Make the effect engine a pure, versioned pipeline: `ImageSource -> Decode -> EffectGraph -> Encode`. Define an effect contract over typed pixel buffers/tiles plus parameters and metadata; register effects by capability. A future frame source can feed the same graph, while WebCodecs plus a muxer handles video/GIF packaging. Keep timing, frame sequencing and encoding outside the still-image pixel-sort kernel. Custom effects then become modules, not UI rewrites.

## Recommended architecture

- **Stack:** React + TypeScript + Vite; Tailwind + shadcn/ui; Worker-based typed-array engine; IndexedDB project store; service-worker PWA; optional WebGPU backend with CPU fallback.
- **Module diagram:** `UI (React controls/canvas)` → `Job coordinator (generation IDs, cancel/progress)` → `Engine interface` → `TS Worker kernel [baseline] | WebGPU [optional]`; `Decode adapter` → `Effect graph` → `Encode adapter`; `Project repository` → `IndexedDB (originals, thumbnails, settings, history)`; `Service worker` → static app shell.
- **Main risks:** browser memory/canvas ceilings on phones; WebGPU support/driver instability; persistence eviction/private mode; decode orientation/color variance; performance targets unproven.
- **Spike 1 — engine benchmark:** implement representative row/column/angled sorting at 12 MP on laptop and mid-range phone. **Pass:** p95 proxy ≤100 ms laptop / ≤150 ms phone, with no UI stalls; export targets in §3 met or documented gap accepted. Compare TS Worker and WebGPU when available.
- **Spike 2 — mobile memory and decode:** import EXIF-rotated, color-profiled 12/24/48 MP JPEGs on iOS Safari and Android Chrome; measure decode, peak memory, canvas release (`width=1; height=1`), and export. **Pass:** 12 MP completes via native canvas without hitting iOS's 384 MB canvas memory cap or tab termination, orientation is correct, and 24/48 MP on iOS either succeeds via tiled decode + Wasm encoder or cleanly enforces a ≤16.78 MP export cap.
- **Spike 3 — persistence/offline recovery:** install to Home Screen (iOS) / via `beforeinstallprompt` (Android), load offline, import image, edit, close/reopen, check `navigator.storage.persisted()`, simulate quota failure and private mode. **Pass:** normal and installed modes restore source/settings/history after restart; quota errors preserve last committed project; iOS tab users see a Home Screen install prompt explaining Safari's 7-day eviction rule; private mode clearly warns that persistence is temporary.
